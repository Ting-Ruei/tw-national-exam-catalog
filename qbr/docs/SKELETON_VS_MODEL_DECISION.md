# 骨架與模型的分工：決定，不是疊層

> 這份文件回答一個問題：**自動化跑起來的時候，誰做什麼、用哪一級的模型、誰監督。**
>
> 它不是「再加一層」的提案。它是一組已經量測過的邊界，寫成可以執行的分工。

---

## 1. 先講結論

| 工作 | 誰做 | 為什麼是它 | 出錯的後果 |
|---|---|---|---|
| 切題、題數、選項歸屬、答案核對 | **程式骨架** | 紙張的性質，量得出來 | 關卡擋住整卷（看得到） |
| 圖片在哪、裁哪裡 | **程式骨架** | 物件座標，量得出來 | 裁切驗證（看得到） |
| 私用區符號對照 | **程式骨架** | 紙本自己在題幹裡寫了 | 對照表顯示在畫面上（看得到） |
| 「哪個字掉了」 | **程式骨架** | 位置是量出來的（字在詞中） | 紅色瑕疵註記（看得到） |
| 大量閱讀、抽語意 | **qwen3.8-flash-next（DGX）** | 便宜、快、讀得一樣好 | 建議，不進正式資料 |
| 文字缺陷守門 | **qwen3.8-27B（本機）** | 缺字 5/5 vs flash-next 1/5 | 建議，不進正式資料 |
| 有爭議時仲裁 | **qwen3.8-27B + thinking ON** | 只在爭議時開，預算 ≥8,000 | 建議，不進正式資料 |
| 接受／退回／修正 | **人** | GOV-05 | 唯一會改正式資料的人 |

**一句話**：骨架決定「這題長什麼樣」，模型只回答「這裡是不是有問題」，人決定「要不要改」。

---

## 2. 骨架做什麼（而且不准模型碰）

骨架負責的是**可以從紙張量出來**的事。下列每一項都有兩個引擎互相驗證，
而且驗收標準是「兩個引擎一致」，不是「測試全綠」：

- **題數**：以答案卷為權威（答案卷是題數的權威）。
- **切題邊界**：後繼號碼；折行不是新題（全庫 89,463 個 anchor 中只有 2 個符合折行條件）。
- **選項歸屬**：私用區字母表（長度等於選項數）、逐家族試切、拒絕為預設。
- **答案**：只從官方答案卷讀（`_ANS`），修正表疊在上面（`_MOD`）。
- **圖片歸屬**：band 規則（自己的題號到下一個題號）。
- **圖片裁切**：取圖物件，不切頁面；墨跡量測排除「有物件但沒畫出來」。

**目前量測**：429/429 卷打包、0 卷被擋、33,150 題、3,516/3,516 兩引擎一致。

### 骨架的三種輸出

1. **資料**（進正式題庫）。
2. **瑕疵**（紅色顯示，例如字形遺失的位址）。
3. **爭議**（兩個引擎不一致 → 交給模型與人）。

**關鍵**：骨架**不猜**。字形遺失就只報位址，不補字；私用區符號沒有對照表就照原樣顯示。

---

## 3. 模型做什麼（而且不准寫入正式資料）

模型只做**骨架量不出來**的三件事：

### 3.1 大量閱讀（flash-next，DGX）

- 32,350 題、0.44 秒/題、併發 16 約 15 分鐘。
- 讀得跟 27B 一樣好（thinking off：兩者都 29/34）。
- 用途：抽語意、分類、產生練習題草稿。

### 3.2 文字缺陷守門（27B，本機）

- 本機 27B 在文字缺陷上明顯較好：

  | 案例 | flash-next | **27B** |
  |---|---|---|
  | 題幹缺字 | 1/5 | **5/5** |
  | 整體缺陷偵測 | 24/35 | **30/35** |

- **三個負對照全部 0 誤報**（三個引擎都一樣）。
- 用途：在題庫上跑一遍，把「這裡可能少一個字」列成建議。

### 3.3 爭議仲裁（27B，thinking ON）

- **只在爭議時開**，預算 ≥8,000 token。
- 理由：thinking ON 在兩個引擎上都要 **51× 牆鐘時間**，換 +3~6% 準確率。
- 用途：兩引擎不一致、或人按「需重看」時，提供第二意見。

### 3.4 一個必須知道的陷阱

**三個引擎有三種 thinking 開關拼法，而且錯的拼法會靜默成功**（HTTP 200、無作用）：

| 引擎 | 關掉推理的寫法 |
|---|---|
| MTPLX | `chat_template_kwargs.enable_thinking`（頂層被忽略） |
| vLLM 8888 | `chat_template_kwargs` **或** `reasoning_effort:"none"`（`"high"` → HTTP 400） |
| mlx-vlm 8082 | **只有**頂層 `enable_thinking`（`chat_template_kwargs` 靜默忽略） |

交付文件寫的「只有 `chat_template_kwargs` 有效」是**錯的**（在 8082 上 ②③ 的輸出與①位元組相同，
代表欄位根本沒到模板；頂層 `enable_thinking=True` 才產生 1,081 字推理）。
**所以開關必須每個引擎雙向探測，不可硬寫。**

## 4. 為什麼是這兩個模型（不是別的）

| 候選 | 決定 | 理由 |
|---|---|---|
| `qwen3.8-flash-next`（DGX 8888） | **用**：大量閱讀 | 0 錯誤到併發 16；prefill ~2,045 tok/s 平到 161K |
| `qwen3.8-27B MTPLX`（本機 8082） | **用**：缺陷守門 + 仲裁 | 缺字 5/5；併發 decode 99.3 tok/s |
| `ornith-1.5-mtplx-35b`（18120） | 不用於本流程 | MTPLX 只有 35b 級堪用，但無量測優勢 |
| `ornith-1.5-mtplx-9b`（18121） | 不用 | 無視覺 |
| `medgemma:4b` / `medgemma:27b` | **不用**（使用者指示） | — |
| Ollama 版本 | **不用**（使用者指示） | 要用 MTPLX 版本 |

**兩台機器不同**（8082 是本機 M5 Max、8888 是 DGX），**可以並行**，不互相搶。

## 5. 誰監督（自動化跑起來的時候）

### 5.1 三條不可跨越的線（GOV-05）

1. **AI 只能建議**：永遠不自動接受、不自動退回、不寫人的審查事件。
2. **模型不進正式資料**：模型輸出是建議，要有人按下才會變成題庫內容。
3. **骨架不猜**：量不到就報位址，不補字、不推演語意。

### 5.2 自動化時人的位置

```
PDF ──骨架──▶ 資料 + 瑕疵 + 爭議
                 │
                 ├─ 資料 ─────────────────▶ 直接進佇列（人只需確認正常）
                 ├─ 瑕疵 ──▶ 紅色顯示 ────▶ 人對照紙本修正（E）
                 └─ 爭議 ──▶ 27B 仲裁建議 ─▶ 人決定
                                              │
                              （唯一會改正式資料的地方）
```

**人的工作只剩兩件**：看紅色、做決定。其餘（切題、題數、選項、圖片、答案）都由骨架完成並
經兩引擎驗證。

### 5.3 三個必看的量測（不是感覺）

| 量測 | 通過標準 | 目前 |
|---|---|---|
| 兩引擎一致 | 每卷題數相同 | 3,516/3,516 |
| 瑕疵是否被標示 | 選項/題幹有失落字形→必有註記 | 0 個未標示 |
| 模型是否亂報 | 負對照誤報 | 0（三個引擎） |

## 6. 「骨架優先」會不會忽略模型？

**不會，而且順序是刻意的**：

1. **先用骨架把能確定的確定下來。** 如果骨架就能回答（題數、切題、選項、圖片），
   就不該問模型——問了只會引進不確定。
2. **只把骨架量不出來的交給模型。** 目前只有三件（閱讀、缺陷、仲裁）。
3. **模型的答案永遠是建議。** 它不會覆蓋骨架，也不需要。

**量測支持這個順序**：模型在「骨架已經能回答」的問題上沒有比較準（閱讀能力兩引擎相同，
且都不比免費的骨架準）。把資源放在骨架量不出來的地方，才是模型該站的位置。

---

## 7. 這一節的規則

1. **先決定，不要疊層。** 每一件工作只有一個負責者。
2. **骨架決定形狀，模型回答疑問，人做決定。**
3. **量得到的不要問模型。** 問了只是把不確定引進來。
4. **開關要雙向探測，不可硬寫**（三個引擎三種拼法）。
5. **空的答案不是模型的證據，是預算的證據**（計分前先檢查空字串）。
6. **一次通過不是通過，是還沒測到**（每個案例要問 5 次）。
7. **AI 只建議**（GOV-05）：不自動接受、不自動退回、不寫人的審查事件。
