# 你的審核紀錄為什麼在 ReviewUI 看不到

> 你問的兩件事：**(1) 要長期用**、**(2) 之前藥師人工審的你現在看不到**。
> 第 2 點你的直覺（是 `/tmp` 的問題）**方向對，但原因不是 `/tmp`**。
> 真正的問題是：**這台機器上有兩套互不相通的審核儲存**。

## 一、結論先講

| | 8765（容器，SQL 後端） | 8774（本機，jsonl 後端） |
|---|---|---|
| 候選題 | **191,819** | 78,690 |
| 學類別 | **32** | 10 |
| 已審 | **19,977** | **175** |
| `/v2` 介面 | ❌ 404 | ✅ 200 |
| 儲存 | Postgres `exam.question_review_events` | `question_review_events.jsonl` |
| 你的藥師紀錄 | ✅ 在 | ❌ 不在 |

**兩邊不是同一個東西的新舊版，是兩個各自累積的儲存。**
你早期在 8765（SQL）審的藥師紀錄從來沒有寫進 jsonl，所以 `/v2` 看不到。

而且兩邊的時間**完全不相交**，所以連「一邊是另一邊的舊版」都不成立：

```
SQL  human events : 2026-06-20  ->  2026-08-18    25,843 筆
jsonl human events: 2026-09-15  ->  2026-09-19       186 筆
                     ^^^^^^^^^^^^ 沒有任何重疊
```

SQL 是**六到八月**的歷史；jsonl 是**九月**你在本機審的。
換句話說：**九月的紀錄不會進 SQL，六到八月的紀錄不會進 jsonl。**

## 五、為什麼 `--carry-from` 救不了這件事

`build_review_queue.py` 的帶入機制（那份 `review_record_safety.md` 寫的）**只掃同層的兄弟佇列目錄**：

```python
previous = sibling_queues_with_reviews(args.out)   # 掃 /tmp 底下的兄弟
```

它看的是**檔案系統**，Postgres 不在它的世界裡。所以：
- `sf7 → sf8 → sf9` 這種重建：安全 ✅（這是那份文件處理的情境）
- SQL → jsonl：**完全沒有路徑** ❌（這是你的情境）

那份報告的結論「紀錄不會被重建弄丟」在**它自己的範圍內是對的**，
但它沒有涵蓋跨儲存這件事。我先前照著它相信 192 筆就是全部，這是我的錯。

## 六、`/tmp` 的角色（你猜對的部分）

`/tmp` 確實有風險，但那是**另一個**風險：

```
/tmp/qbr-all-queue   185M   上次重開機就會消失
/tmp/qbr-live-sf9    255M   同上
```

它不會讓你的紀錄「在 UI 看不到」（紀錄在 SQL），但會讓**整個佇列**消失。
我已經先做了這件事：

```
qbr/data/review-queues/live/review-ui/     ← 持久路徑
  candidates.jsonl               78,690 題
  question_review_events.jsonl       192 筆
  queue_index.json
8774 已改指到這裡（不再指 /tmp）
```

`qbr/data/` 在 `.gitignore` 內，不會進版控，但**在 repo 目錄下**，重開機不會消失。

## 七、同一件事發生在測試上（我先把這個修好了）

在調查你的紀錄時，我注意到 `qbr` 的測試從 **237 passed** 變成 **220 passed / 17 skipped**。
**總數沒變（237），但 17 個測試從「通過」變成「跳過」——這是靜默的覆蓋率損失。**

原因**跟你遇到的問題是同一種**：那 17 個測試讀 `/tmp/qbr-golden-001`、`/tmp/qbr-golden-002`
的真實產物。這兩個目錄被清空了（只剩 `review-ui/question_review_events.jsonl`），
測試的 `skipif` 就把「**讀不到證據**」靜默地變成「**不必驗**」。

```
RUNS = [p for p in ("/tmp/qbr-golden-001", "/tmp/qbr-golden-002")
        if os.path.isfile(os.path.join(p, "run_manifest.json"))]
requires_run = pytest.mark.skipif(not RUNS, reason="no golden-path run to inspect")
```

**已修復並驗證**：

| 檢查 | 結果 |
|---|---|
| 重建 golden-001 / 002 | 80 題、七階段全過（含 S6 verify） |
| 與 git 追蹤的 `tests/golden/…jsonl` 逐欄比對 | **逐欄相同** |
| 送分題（Q10/Q41） | `送分` / `is_special_correction=True` ✓ |
| 兩次重建 `questions.jsonl` sha256 | 相同（冪等）✓ |
| `pytest tests/` | **237 passed, 0 skipped** |

這不是「剛好也在 `/tmp`」，而是**同一條規則**：
證據放在 `/tmp`、取不到時靜默降級。你的審核紀錄是「靜默不顯示」，
測試是「靜默不驗」。**兩者的共同修法不是記得備份，是讓缺席變可見。**

## 八、還沒做（需要你決定）

兩個儲存要合併，有兩條路，**差別在「用哪邊的紙本」**：

### 路線 A：`/v2` 改接 SQL（保留你的 19,977 筆）

- 你的紀錄**立刻全部回來**，不用搬任何資料
- 代價：SQL 的內容是 **v0.4 解析器**（176,021/191,839），
  **沒有**我這次修的 `⻑`→`長` 偵測，也沒有新管線的上下標修復

  與沙盒「**儲存的字永不重寫**」原則的關係需要先確認——這點我還沒查清

### 路線 B：把 SQL 紀錄灌進 jsonl 佇列（保住新管線的內容）

- 新管線的內容留著（`⻑` 偵測、上下標修復都在）
- 16,355 題直接沿用、3,336 題走 `reset_review` 重新確認
- 我已經寫好工具並量過：`qbr/scripts/carry_sql_reviews_to_queue.py`
  （分類規則：NFKC 後相同→carry；實質不同→reset；題目不在→orphan）
- 提案已產生 `/tmp/sql_carry_proposal.json`，**尚未寫入任何檔案**

### 兩條路的共同前提

**「內容品質」與「審核歷史」目前在不同邊。** SQL 有歷史但內容舊；
新佇列內容新但沒有歷史。不管走哪條，都要先決定**哪一份紙本是準的**，
否則就是在兩個都能不一致的地方各留一份。

## 九、這件事的教訓（給下一個人）

1. **「紀錄不會丟」的驗證要問「哪些紀錄」**。我驗的是「重建 3 次都是 186 筆」，
   而真正的 19,867 題從來不在我驗的那個檔案裡。**驗一個子集不會證明全集安全。**
2. **兩個做同一件事的東西，就是兩個可以不一致的地方**（charter 原話）。
   這裡有兩個 review backend、三個 UI 埠、兩個儲存——正是這句話的實例。
3. **使用者說「我沒看到」時，先去看他看的那個畫面**。
   我先前一直在量 `/tmp` 佇列，卻沒有問「8774 到底指到哪」。
