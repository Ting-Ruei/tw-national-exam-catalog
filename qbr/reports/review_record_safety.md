# 審核紀錄不得被重建弄丟（2026-09-19）

## 這份文件回答一個問題

> 我按下 W/S 審題、按下 A/R/B 記錄決定，之後你重建題庫，我的紀錄還在不在？

現在答案是**在**，而且不是靠「記得加參數」在，是靠**結構上不可能忘**。

## 一、紀錄寫在哪（先確認事實）

服務指令列就是答案：

```
serve_question_review_ui.py \
  --candidate-jsonl /tmp/qbr-live-sf9/review-ui/candidates.jsonl \
  --review-log     /tmp/qbr-live-sf9/review-ui/question_review_events.jsonl \
  --review-backend jsonl --port 8774
```

- 寫入用 `open("a")`（append-only，第 3972 行），**只增不改**。
- `/v2` 以 `no-store` 從磁碟讀（第 1787 行），所以改 HTML **不需要重啟**，也不可能碰到紀錄。

動工前後比對：`144` 筆、md5 `ec0d4086d009df969b7c79ca7148eb0a`，**完全一致**。

## 二、原本的危險在哪（你提醒的那一點）

`build_review_queue.py` 的 `--carry-from` **原本只在「原地重建」時預設安全**：

```python
previous = [args.out] if os.path.isdir(...) else []   # 重建到新目錄 -> 什麼都不帶
```

而本專案實際做法就是重建到新目錄（`sf7 → sf8 → sf9`）。也就是說：
**用正常操作就會踩到**。實測 `--out /tmp/qbr-live-sf10` 會帶入 **0 筆**，
而 `/tmp/qbr-live-sf9` 裡躺著 **144 筆**人工決定。

## 三、修好之後

三層，由內而外：

1. **自動帶入（預設行為，沒有旗標可忘）**
   `sibling_queues_with_reviews()` 找出同一個 `/tmp` 下所有含紀錄的兄弟佇列，
   加上目的地自己，全部帶入。實測：**392 筆自動帶入，0 孤兒**。
   `--carry-from` 改為**加乘**而非取代（原本會互相打架，導致正確用法被拒）。

2. **去重鍵修正（真正的 bug）**
   `_carried_from` 是「從哪來」的標記，卻被算進去重鍵的一部分，
   於是每次重建都把同一筆當成新的。實測：第一次 **392** 筆，再建一次 **629** 筆
   ——同一批 181 題全部出現兩次，再建下去會是三次。
   改為：去重前先 `pop("_carried_from")`。
   驗證：連續重建三次都是 **186** 筆（＝各佇列相異事件的聯集，獨立算出也是 186）。

   去重仍以**整筆紀錄**為單位，不是 `candidate_key`：同一題合法地會有
   `block` 之後 `accept`（審核者改變決定），用題號去重會靜默丟掉後面的決定。
   實測有 3 題是這種情形，都完整保留。

3. **最後一道防線**
   要寫出「一筆都不帶」的佇列而旁邊有紀錄時，**拒絕啟動**（退出碼 2），
   且在 `merge` 之前檢查，所以拒絕時目的地完全沒被動過。

## 四、量測（不是推論）

| 情境 | 結果 |
|---|---|
| 不帶任何旗標重建到新目錄 | 392 筆自動帶入，0 孤兒 |
| 連續重建 3 次 | 186 / 186 / 186 筆（不成長） |
| 獨立計算的相異事件聯集 | 186 筆（相符） |
| 同一題多事件（block→accept） | 2 筆都保留 |
| 題目已消失的孤兒紀錄 | 保留並計數，不丟棄 |
| 動工前後 live 紀錄 | 144 筆、md5 相同 |
| 測試 | `tests/test_review_queue.py` 16 passed；全套 201 passed |

## 五、還沒解決的（誠實列出來）

1. **跨機器／跨根目錄的兄弟佇列不會被自動找到。** 目前只掃 `--out` 的同層目錄。
   若紀錄在別的磁碟區，仍需 `--carry-from`。
2. **紀錄與佇列的綁定仍是「檔案在旁邊」**，不是資料庫交易。服務用 JSONL 後端時，
   寫入與重建之間若同時發生，仍有極小的競態窗口。
3. **重建期間服務應暫停**。`/v2` 每次請求重讀磁碟，所以重建到**正在服務的目錄**時，
   列表與候選檔會有短暫不一致。這是之後要更嚴謹處理的部分。
