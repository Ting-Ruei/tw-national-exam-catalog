## 1. 怎麼量（三個獨立來源，沒有一個是被測模型）

| 用途 | 來源 | 為什麼獨立 |
|---|---|---|
| 題號位置、題幹範圍、圖片物件位置 | **`pdftohtml -xml -zoom 1.0`**（poppler） | 不是我們的 parser、不是被測模型 |
| 墨跡（哪些像素是內容） | **渲染後的像素**（luma < 200） | 不取決於 PDF 作者怎麼畫 |
| 預測 | **PP-DocLayout-V3 ONNX**（CPU） | 被測物 |

### 1.1 題號 span 的推導（含兩個修好的缺陷）

- **題號＝行首的「數字＋`.`」**，且必須在頁面左緣 36pt 內（題幹起於 28pt、選項起於 39pt）。
- ⚠️ **缺陷一：題號與題幹被拆成兩個 text 節點。**
  1152 卷是 `30.病患因為...`（同一節點），1072 卷是 `'22.'` 單獨一格、題幹另一格。
  原本的 regex 要求「點後面要有字」→ 1072 卷**一個題號都抓不到**（歸屬全 null）。
  已修正為「只要數字＋點」。
- ⚠️ **缺陷二：圖在頁首、題幹在前一頁。**
  1152 卷 page 16：兩張照片在 y29–286，但該頁第一個題號是 79（y400）——
  那兩張照片屬於**上一頁的 Q78**。不做 carry-in 就會「歸屬到空氣」。
  已改為**由上一頁最後一個題號帶入**（不是假設 `first - 1`）。

### 1.2 兩個量測缺陷（都是我的指標錯，不是模型錯）

⚠️ **缺陷三：歸屬用「IoU > 0.1」判定是錯的。**
1072 卷 page 13 有一筆被判錯，量下去發現**偵測器把一張大圖正確切成 4 塊、4 塊全在 Q77 內**，
只是第 3 塊與整塊真圖的 IoU 是 **0.093**，剛好低於門檻。
→ **歸屬與「框多貼」是兩件事。** 已改為：預測框**覆蓋最多的真圖**落在哪個題號，
就與預測自稱的題號比對。**改完 1072 卷 10/11 → 11/11。**

⚠️ **缺陷四：拿「PDF 圖片物件的範圍」當範圍 GT 是錯的。**
PDF 物件**帶著作者畫的空白邊**。實測空白佔比：**1152 卷平均 77.4%、1072 卷平均 93.9%**。
→ 一個「貼著內容的緊框」會因為**框得比 PDF 物件更緊**而被扣分。
page 13 的 coverage 0.673 就是這樣來的：四張結構圖**全在框內**，只是框沒有含 PDF 物件的空白。
→ 已改用**墨跡指標**（見下）。

### 1.3 墨跡指標

- **ink_recall** ＝ 圖區域內的墨跡，落在預測框內的比例 → *圖有沒有留住*
- **ink_added** ＝ 預測框內、但在圖區域**外**的墨跡 → *有沒有夾帶別題的內容*
  （這才是審題者會看到的失敗：裁切把隔壁題的字一起吃進來）

## 3. 三個視覺驗證（第二引擎，不是算術）

用 `probes/render_figure_overlay.py` 把 **GT（藍/橘）**、**預測（紅）**、**題號 span（綠）** 畫在同一頁上，用人眼看。

### page 16（1152）——**偵測器比 GT 更準**

- GT（橘）＝**一大塊**：PDF 把兩張照片畫成 **7 條全寬橫條**，`pdftohtml` 無法分開。
- 預測（紅）＝**正確切成兩張照片**，兩框都標 `q78`，都落在 Q78 的 span 內。
- **這一頁上人眼判定：偵測器對、GT 錯。** 這正是「單框 IoU 只有 0.491 但 coverage 0.965」的原因，
  也是為什麼要**兩個引擎**：算術說 IoU 低，圖說框是對的。

### page 9（1152）——切開是設計，標籤是另一類

- 偵測器把三張小圖**正確切成三塊**，三塊都標 `q43`。
- ⚠️ 但它**沒把圖下方的印刷標籤（圖一/圖二/圖三）算進 figure 類**——
  查下去那三條是 **`figure_title` 類**（信心 **0.855–0.861**），**偵測器有找到，是我的 figure 類沒收它**。
- 補上 `figure_title` 後：**ink recall 0.956 → 0.993**，缺口從 4.4% 降到 0.7%。
  → **這一筆「缺口」不是模型漏框，是標籤被歸到別類。**（`FIGURE_TITLE` 已分開記，兩個數字都報。）

### page 13（1072）——GT 的空白邊

- 真圖是**四個化學結構**（PDF 物件範圍 y385–786），中間夾 **19pt / 52pt / 28pt 空白**。
- 偵測器給四個**緊框**，各自貼住一個結構。
- 墨跡 recall **0.997** → **內容全留住**。coverage（對 PDF 物件範圍）只有 0.673 → **扣分扣在空白**。
- **人眼判定：四個框是對的。**

### ⚠️ 唯一的真夾帶（1072 卷 page 9，36 px）

36 像素落在**同一個題號（Q58）**的圖區域之外，但**仍在 Q58 的題幹 span 內**——
即**框稍微超出圖、吃到自己題目的內文邊緣**，**不是隔壁題**。屬可接受。

## 4. 讀到的三件事

1. **歸屬沒有量到任何錯誤（20/20）。** 題號 span 是從**文字層**推導的，
   PP-DocLayout 不需要知道題號，兩者對上——**這是兩個獨立來源一致**。
2. **範圍留得住內容（0.99）、且不夾帶別題（0–186 px）。** 切開（一張圖多框）是它的工作方式，
   不是錯誤；面積／墨跡指標才看得出來。
3. **「cut 對不對」不能只用一種 GT 量。** PDF 物件範圍**含 77–94% 空白**，
   用它當 GT 會懲罰正確的緊框。**墨跡才是獨立量尺。**

## 5. ⚠️ 尚未量 / 尚未解（**不要當已知**）

1. **只有 2 份卷、11 頁、12 題。** 樣本小，**不可外推**成全題庫的比率。
2. **掃描件完全沒量。** 掃描 PDF 無圖片物件、`pdftohtml` 報「整頁一張 bitmap」→
   **歸屬的 GT 要另立**（人工標或另一套方法）。**這是最大的未知。**
3. **表格（`table`）完全沒量。** 本輪 12 題全是 `image`。
4. **`--threshold` 固定 0.3**（SDK 預設），**precision/recall 曲線沒量**。
5. **DPI 固定 150**，低 DPI 對小結構圖的影響**沒量**。
6. **`order_logits`（閱讀順序）沒用**——它可能對「圖屬於哪一題」提供**獨立第三來源**，未驗。
7. **`out_masks`（多邊形）沒用**，只用矩形框。
8. **未與 MinerU 的 layout 對比** → **還沒做到「兩引擎各自量，再比對」**（目前是「模型 vs poppler」，也算兩引擎，
   但 MinerU 是我們**現行 pipeline 實際在用的**，更該比）。
9. **跨頁圖（圖在頁首屬前一頁題）只遇到 1 例**（1152 p16），carry-in 只驗過這一例。

## 6. 建議

1. **下一步做「掃描件的歸屬」** —— 這是唯一**完全沒量**且**題庫裡一定有**的情況。
   要另立 GT（渲染頁 → 人工標題號位置，或與 MinerU 的 block 對照）。
2. **與 MinerU 的 layout 對比** —— MinerU 是現行 pipeline 在用的，比它才有決策意義。
3. **量 `table` 類** —— 表格截圖在題庫裡是另一類（本案只有 15 張）。
4. **調 `--threshold` 掃一次曲線** —— 目前 0.3 是預設值，沒有理由。
5. **若要把多框合成一個裁切**：直接**取同一題號所有框的聯集**（並集 padding 少）。
   實測每題的框 union 都能覆蓋 0.99 的墨跡，且不夾帶別題。
