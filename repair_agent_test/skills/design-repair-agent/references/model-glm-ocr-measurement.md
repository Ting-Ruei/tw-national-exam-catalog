## 1. 安裝與執行（可重現）

```bash
mkdir -p ~/models/glm-ocr && cd ~/models/glm-ocr
~/models/venvs/mlxenv/bin/hf download mlx-community/GLM-OCR-4bit --local-dir GLM-OCR-4bit

~/models/venvs/mlxenv/bin/python -m mlx_vlm.generate \
  --model GLM-OCR-4bit --image PAGE.png \
  --prompt "Text Recognition:" --max-tokens 8192 --temperature 0
```

- **沒有新增依賴**：`mlx_vlm 0.7.1` 已有 `mlx_vlm/models/glm_ocr/`（`config.py`／`vision.py`／…）。

  [`../../../probes/compare_ocr_to_reference.py`](../../../probes/compare_ocr_to_reference.py)。

（`time` 是內建的，不是 shell 的），直接 redirect 會把計時行寫進文本。**建議分離 stdout 與 stderr**。

## 3. 準確度 — 三組實驗

比對方法：漢字（CJK）多重集合 ＋ 序列相似度。**ground truth 一律是「官方 PDF 的文字層」**，
不是我們的判讀、也不是模型自己的另一輪輸出（避免循環驗證）。

### 實驗 A：數位原生頁（`pharmacy-1022-analysis/pages/page-{1..5}.png`）
Reference = `pages.jsonl` 的 `consensus.text`（pdfplumber／poppler／pypdf 三家共識，
pairwise similarity 皆 > 0.993）。

| 頁 | 字元相似度 | 漢字數 GLM / ref | **漢字差異** |
|---|---:|---|---|
| 1 | 0.9409 | **557 / 557** | `试`→`試`、`滁`→`滌`、`氩`→`氫`、`爲`→`為`、`溵`→`澱` |
| 2 | 0.7435 | — | `爲`→`為`(4)、`哪`→`那`(1) |
| 3 | 0.8734 | — | `氩`→`氫`(8)、`爲`→`為`(4)、`訳`→`訊`(2)、`一`→（衍）|
| 4 | 0.9392 | — | `爲`→`為`(15)、`擼`→`高`+`壓`、`渗`→`滲`、`氙`→`燈`、`擔`→（移） |
| 5 | 0.9752 | — | `爲`→`為`(7) |

**漢字總數幾乎總是相等（page1：557/557）→ 它不會漏字、不會多字；錯在「字形認錯」。**

**為什麼 page-2 相似度只有 0.74？** 不是因為內容錯 —— 是它把數學式輸出成 **LaTeX**：
`（$A = \varepsilon \times I \times c$）`、`1:1`、`$\textcircled{1}$`、`$_3$`。
**同頁漢字差異只有 `爲`×4 ＋ `哪`→`那`×1**。→ **相似度低是「格式標記」造成的，不是辨識錯誤。**

### 實驗 B：掃描件（`old_scans`，官方自陳最弱 37.6）
樣本：`語言治療師/104/第2次/1042_…構音與語暢障礙學.pdf`（**無文字層**，`pdftotext` 抽 0 字）
以 `pdftoppm -r 150` 渲染第 1 頁。

**結果：`real 4.4s`，80 題的完整第 1 頁全部讀出**，內容與 MinerU 輸出可逐題對上。

### 實驗 C：**兩引擎一致**（GLM-OCR vs MinerU，同一掃描頁、同一題號範圍 1–8）

| 指標 | 值 |
|---|---:|
| 純文字相似度（去空白） | **0.996** |
| **漢字多重集合相似度** | **1.0** |
| **漢字數 GLM / MinerU** | **413 / 413** |
| 差異 | 僅 `∅` vs `ø`、`k$^{h}$` vs `k^h`、`\_` vs `_`（LaTeX／跳脫字元） |

**→ 兩個完全不同的引擎（MinerU vs GLM-OCR）在掃描件的漢字上完全一致。**
這是 `qbr/AGENTS.md`「**兩引擎一致才是驗收**」可以據以成立的一筆證據。
**注意：這一筆只覆蓋 8 題、1 頁，不能外推。**

## 4. ⚠️ 最重要發現：系統性繁簡／異體字混淆

**這不是隨機錯誤，是固定模式。** 五頁全部出現：

| GLM-OCR 輸出 | 正解（紙本） | 出現次數 |
|---|---|---|
| `爲` | **`為`** | 1+4+4+15+7 = **31** |
| `氩` | **`氫`** | **9** |
| `试` | **`試`** | 1 |
| `滁` / `渗` | **`滌`** / **`滲`** | 2 |
| `訳` | **`訊`** | 2 |
| `擼` | **`高壓`**（拆成兩字） | 1 |
| `溵` | **`澱`** | 1 |
| `哪` | **`那`** | 1 |

**判讀（我的判斷，非事實）**

- **它對繁體中文並沒有真正的字形知識**——模型卡語言清單只有 `zh`，**沒有繁體**。
  遇到繁中罕用／異體字形，它會**回退到簡體或形近字**。
- `爲` 是 `為` 的**異體字**，筆畫近似；`氩`（簡體）vs `氫`（正體）也是形近。
  **這是一個「字形空間」問題，不是「解析度」問題**——提高 DPI 未必能解。
- **對本案的致命性**：`qbr/AGENTS.md` 的判定詞彙裡有 `substituted-ideograph`（異體字替換），
  而且 `apply_dispute_repairs.py` 會**自動套用**這一類修復。
  **如果 GLM-OCR 的輸出被當成「正確紙本」餵進判讀迴圈，它會製造一整批假的「異體字缺陷」。**
  → **GLM-OCR 的輸出不可以直接當 ground truth；只能當「第二意見」。**

**這一項是採用 GLM-OCR 的**閘門**，必須先解。**

## 5. 其他量到的事實

- **不吃自由指令**（模型卡「Prompt Limited」）：只認 `Text Recognition:`／`Formula Recognition:`／
  `Table Recognition:` 與嚴格 JSON schema。**它不會回答「這題錯在哪」。**
- **會輸出 LaTeX**：數學式變 `$\varepsilon$`、圈號變 `$\textcircled{1}$`、上下標變 `$_3$`／`$^{h}$`。
  **對「純文字對差」是好事**（結構化），**對「字元級比對」是雜訊**（page-2 相似度 0.74 的主因）。
- **排版會被壓縮**：它把 `(A)(B)(C)(D)` 併成同一行，MinerU 則一行一個。**行數不可比。**
- **不會漏字、不會多字**（漢字數經常精確相等）。
- 掃描件（無文字層）**讀得出來**，這一項**比預期好**。

  —— **三者都還沒試。**

## 7. 我的建議（**未執行**）

1. **先解繁簡閘門**，再談採用。最小實驗：同一頁跑 4bit 與 8bit／bf16，
   看 `爲`／`氩` 這類錯誤是否隨精度消失。
2. **若閘門不解**：把 GLM-OCR 定位成**「第三意見的偵測器」而非「正確答案」**——
   它與 MinerU **不一致的地方**才值得人看，而不是拿它的輸出直接覆蓋。
   （這反而**正好對中**「兩引擎不一致」面板的設計。）
3. **優先試 `Table Recognition:` 與 JSON schema 抽取**，那才可能是它真正贏過現行路徑的地方。
4. **不要**在解閘門前把它接進 `apply_dispute_repairs` 的路徑（那條會自動套用 G2/G3）。
