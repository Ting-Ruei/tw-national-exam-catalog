# 審題介面路線史（舊 → 現在）

這份文件存在的原因是：**過去走不通的部分，要記下它為什麼走不通**，
否則同一個設計會被重新想出來，而且看起來還是很合理。

只記介面路線。管線本身的路線見 [`../qbr/PROPOSED_WORKFLOW.md`](../qbr/PROPOSED_WORKFLOW.md)
與 [`../qbr/reports/compare_three.md`](../qbr/reports/compare_three.md)。

---

## 現況（一句話）

| 介面 | 狀態 | 檔案 |
|---|---|---|
| **v2 · 線性審題** | **基準線**，唯一維護中 | `review_ui/v2.html`（`/v2`） |
| v1 · 隨身審題（手機快速分流） | 僅供參考 | `review_ui/v1-reference/mobile.html`（`/mobile`） |
| v1 · 例外工作台（八線道） | 僅供參考 | `review_ui/v1-reference/workflow.html`（`/workflow`） |

**v1 仍然服務**，因為既有書籤、已安裝的 PWA、以及會送 `mobile_defer` / `mobile_resume`
事件的消費者都是契約。一個更好的介面沒有權利因為它更好就把它們弄壞。
而且刪掉 v1 會讓「新的比舊的好」變成沒有對照組的主張。

## 舊路線一：把題目分派到「線道」

v1 的工作台把每題分到一個 **主要 queue**，其餘 lane 留在題目時間線：

```js
const LANES = ['answer', 'group', 'notation', 'text_evidence', 'vision'];
```

畫面是 `repeat(5, ...)` 的格子，每格一張 lane card，帶 `machine_pass` / `finding` / `failed` /
`skipped` 四種狀態。

**它想解決的問題是真實的**：一題可能同時有答案疑問、題組關係、記號問題、文字證據問題、
圖片問題，而一次只給人看一種。

**它為什麼不是基準線**：

1. **它把「機器找到什麼」變成導覽結構。** 線道是**機器輸出的分類**，不是紙張的性質。
   於是機器的分類錯的時候，人的動線也跟著錯 —— 而且人是在被誤導的動線裡判斷機器。
2. **它讓一題沒有單一位置。** 「每題只進一個主要 queue」需要一個**分派規則**，
   而分派規則本身又要被維護。題目在畫面上的位置取決於分類器，不取決於卷。
3. **它把「審完一卷」變成不可能的目標。** 八線道是**例外導向**的：
   它適合「處理剩下的問題」，不適合「把這份卷讀完」。
   而實際的工作是後者 —— 審題者要的是「這卷 80 題我都看過了」。

v2 的答案是把**順序還給卷**：一份清單，一題，四個決定，`W`/`S` 前後走。
機器的發現不再決定動線，而是**畫在題幹之上**（爭議）與**變成濾鏡**（未看 / 需重看・阻擋 / 爭議 / 有圖）。
濾鏡是**人選的**，不是機器分派的。

## 舊路線二：手機快速分流的決定詞彙

v1 的手機介面用一組**刻意很小的**決定詞彙，由伺服器映射成 review event：

```python
action_by_disposition = {
    "accept": "accept",   "reject": "block",   "note": "needs_review",
    "defer": "mobile_defer", "resume": "mobile_resume",
}
```

**保留到現在的**：這個映射沒有動。`mobile_defer` / `mobile_resume` 仍然是事件的合法值，
因為已經安裝的 PWA 會送它們。**事件詞彙是契約，介面不是。**

**沒有保留的**：`defer`/`resume`（延後/繼續）這個概念本身。
在線性審題裡「稍後再看」沒有意義 —— 題目就在清單裡，`W`/`S` 隨時走得到，
而「延後」只是一種把題目從眼前移開卻假裝它被處理過的方式。

## 舊路線三：讓濾鏡只改「畫什麼」

這是**最值得記下來的一個**，因為它看起來完全合理，而且有一條聽起來很有道理的原則在支撐它。

v2 早期的設計：chips 只縮小**被畫出來**的清單，`W`/`S` 走**整個 scope**。
程式裡甚至有一行註解替它辯護：

> A filter narrows what is drawn, not what is walked.

辯護的理由是「濾鏡不該在游標底下重新排列清單」。那個理由在**它自己的前提裡**是對的 ——
問題是它用「讓導覽忽略清單」來達成「清單不重新排列」。**它保住了清單的穩定，代價是導覽不再指向清單。**

**量到的後果**（真的佇列，題組選取，一組在 78–80）：

| 動作 | 舊行為 | 清單顯示 |
|---|---|---|
| 在 80 按 `S` | 跳到**下一卷的第 1 題** | 下一組 |
| 有圖 + `S` | 靜默離開濾鏡 | 下一張有圖的題 |
| 題組 + `S`（單卷） | 走過 **72** 題非題組題 | 8 題 |
| 題組 + `S`（跨卷 sitting） | 走過 **474** 題 | 6 題 |

審題者不可能知道自己看過哪些題 —— 因為他走過的和他看見的是兩份不同的集合。

**修法就是那條 charter 規則**：**導覽與內容必須來自同一個來源**。
`S.rows` 同時是被畫出來的陣列與被走過的陣列。
（`S.view` 留著整個 scope，因為 chips 上面的計數與分類麵包屑是**對 scope** 的陳述，
不是對濾鏡的陳述 —— 一個會因為別的 chip 被選而改變數字的 chip 沒人讀得懂。）

---

## 兩條規則的對照

| 舊規則 | 現在 |
|---|---|
| 濾鏡只改「畫什麼」，不改「走什麼」 | **濾鏡同時改「畫什麼」與「走什麼」** |
| 每題分派到一個線道，導覽跟著線道 | 導覽跟著**卷**；機器發現是**濾鏡**與**爭議** |
| 一題在畫面上的位置由分類器決定 | 由**卷的順序**決定 |
| 「稍後再看」是一種狀態 | 題目就在清單裡，不需要那個狀態 |

---

## 從 v1 帶過來、應該保留的

- **決定詞彙與事件契約**（含 `mobile_defer` / `mobile_resume`）：已安裝的客戶端是契約。
- **「每題只進一個主要清單」** 這個直覺：v2 用「一份清單」實現它，不是用「分派」。
- **機器發現要看得見**：v2 用爭議（畫在題幹之上）與濾鏡實現它。

## 從 v1 帶過來、應該丟掉的

- **導覽跟著機器的分類。**
- **例外導向的動線**（適合處理剩下的問題，不適合讀完一份卷）。
- **以「延後」代替「決定」。**
- **讓濾鏡與導覽分家。**

## 錯題討論區：為什麽曾經「愈解釋愈消失」

這個區的成員資格不是「這題壞掉」，而是「**這題最新的狀態是一個待複核的重置**」
（`reviewStatus=discuss` 對應 `repair_pending` / `accepted_reaudit` / `reset_review`，
再加上人按的 `block`）。而事件紀錄把**最後一筆事件**當成題目的狀態。

註解是 `action=comment`。伺服器有一個 `_reaffirm_standing_action`，它會把註解的 action 改回它
底下那個決定——但只限 `STANDING_ACTIONS` 裡的动作，而 `reset_review` **不在裡面**。

所以：`reset_review` → 題目進入討論區 → 審題者寫下「我為什麼卡住」 → 那筆 `comment` 成為最新事件
→ 待複核的重置被清掉 → **題目離開卡住的清單**。你愈解釋，它愈消失。而且畫面上看起來就是
「我寫完註解，它就不見了」，沒有任何錯誤訊息。

修法是把「這是待複核重置上的一則註解」寫成**一個**函式（`_note_annotates_pending_reset`），
每一個折疊點都用它：JSONL 載入、SQL 載入、以及兩個記憶體內更新路徑。註解**併入**待複核的重置，
人的字在 `notes`、修復的標記留在 `reset_notes`（`review_projection` 先讀 `reset_notes`，所以
`repair_pending` 仍然成立）。真正的判決仍然會清掉重置——修好的是「註解不是判決」這件事。

負對照：`scripts/test_v2_note_keeps_question.mjs` 在隔離的 server 上真的按「儲存註解」；把修法還原，
那一題就從 1 題變成 0 題（實測）。`tests/test_review_ui_note.py` 另外釘 SQL 折疊那一半。

## 錯題討論區的版面：跟題目審核區同一個算式

舊版面是 `214px | 1fr | 330px`——右邊的紙本只有題目區給同一份文件的大約四分之一。
而這一區的工作（拿抽取文字對紙本、缺圖就裁）比題目區**更需要**那張紙。
題目區是 `238px` 清單 + `.compare` 的 `1fr 1fr`，所以討論區改成同一個算式：
`238px | 1fr | 1fr`。實測 1680 寬的視窗：紙本欄從 330px 變成 721px，與題目區的 721px 一致。

這一條只有實測才算數：`scripts/test_v2_ui_audit.mjs` 會量出兩個區的紙本框寬度。

## 未解

1. **重建進「正在服務」的目錄時，列表與候選檔會短暫不一致。** 重建期間應暫停服務。
   這是**介面層看得到**的症狀，根因在重建流程：見 `qbr/reports/review_record_safety.md`。
2. **v1 沒有移除，也沒有測試。** 它現在是「開著但沒人驗」的狀態。
   只要它還服務，就還可能被使用者打開；目前沒有機制偵測它已經壞掉。
3. **v1 與 v2 的分岔只有靠紀律維持**（v1 只修「讓它能動」的問題）。
   沒有任何自動檢查阻止有人往 v1 加功能。
